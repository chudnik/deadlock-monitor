# Deadlock Monitor

Проект демонстрирует монитор управления ресурсами с предотвращением взаимных блокировок (deadlock) в многопоточной среде.  
Главный результат проекта — класс `ResourceMonitor`, который безопасно распределяет ресурс между потоками и допускает выделение только при сохранении безопасного состояния системы.

## Что реализовано

- Монитор ресурсов с потокобезопасным API.
- Предотвращение deadlock на основе алгоритма банкира.
- Валидация входных параметров и инвариантов (с исключениями).
- Симуляция работы потоков поверх монитора для демонстрации поведения.
- Журнал событий и итоговая статистика по потокам.

## Монитор ресурсов (ядро проекта)

Ядро находится в:

- `src/monitor.hpp`
- `src/monitor.cpp`

Монитор хранит и синхронизирует состояние:

- `Total` — общее число единиц ресурса;
- `Available` — доступные единицы ресурса;
- `Max[i]` — максимальная потребность потока `i`;
- `Allocation[i]` — уже выданные потоку `i` единицы;
- `Need[i]` — оставшаяся потребность (`Max[i] - Allocation[i]`).

Ключевые инварианты:

- `Allocation[i] >= 0`, `Need[i] >= 0`;
- `Allocation[i] + Need[i] = Max[i]`;
- `sum(Allocation) + Available = Total`.

## API монитора и инварианты

Публичный API `ResourceMonitor`:

- `request(thread_id, amount) -> bool`
- `release(thread_id, amount)`
- `shutdown()`
- `snapshot() -> StateSnapshot`
- `getNeed(thread_id) -> int`
- `stats() -> const std::vector<ThreadStats>&`

Поведение и контракты:

- `request` блокирует поток, пока выделение не станет безопасным.
- `request` возвращает:
  - `true` — ресурсы выданы;
  - `false` — монитор завершает работу (`shutdown`), запрос не выдан.
- `release` возвращает ранее выданные ресурсы и пробуждает ожидающие потоки.
- `shutdown` выставляет флаг завершения и будит все потоки, ожидающие в `request`.

Проверки аргументов:

- Для `thread_id`: диапазон `[0, num_threads)`, иначе `std::out_of_range`.
- Для `amount`: должно быть `> 0`, иначе `std::invalid_argument`.
- Для `request`: `amount <= Need[thread_id]`.
- Для `release`: `amount <= Allocation[thread_id]`.
- Для конструктора:
  - `total > 0`, `num_threads > 0`;
  - `max_claims.size() == num_threads`;
  - `0 <= max_claims[i] <= total`.

## Как монитор предотвращает deadlock

Монитор использует алгоритм банкира:

1. При `request` выполняется гипотетическое выделение (`Available`, `Allocation`, `Need` временно меняются).
2. Запускается проверка `isSafe()`: существует ли безопасная последовательность завершения всех потоков.
3. Если состояние безопасно — выделение подтверждается.
4. Если небезопасно — изменения откатываются, поток ждет на `condition_variable`.

Таким образом, монитор не допускает перехода в небезопасное состояние.

## Архитектура и роль остальных компонентов

- `src/main.cpp` — CLI orchestration:
  - чтение аргументов;
  - запуск симуляции;
  - вывод итоговой статистики.
- `src/simulation.cpp` / `src/simulation.hpp` — демонстрационный контур:
  - генерация `Max[i]`;
  - поведение worker-потоков;
  - таймер остановки симуляции и вызов `shutdown`;
  - форматирование runtime-логов.

Симуляция нужна, чтобы показать работу монитора в динамике; бизнес-логика распределения ресурсов находится в `ResourceMonitor`.

## Сборка

Требования:

- C++17-совместимый компилятор (GCC/Clang/MSVC);
- CMake 3.16+.

Команды:

```bash
cmake -S . -B build
cmake --build build
```

После сборки исполняемый файл: `build/monitor`.

## Запуск

Формат:

```bash
./build/monitor <threads> <total_resources> <duration_sec>
```

Пример:

```bash
./build/monitor 5 20 10
```

Где:

- `threads` — число потоков;
- `total_resources` — общий объем ресурса;
- `duration_sec` — длительность симуляции в секундах.

## Формат логов и статистики

Логи событий имеют единый формат:

```text
[+   123ms] event=REQUEST thread_id=2 amount=3 state={avail=5 alloc=[...] need=[...]}
```

Основные события:

- `REQUEST` — поток запрашивает ресурс;
- `GRANTED` — монитор выдал ресурс;
- `RELEASE` — поток освободил ресурс;
- `COMPLETE` — поток завершил работу (когда `need == 0`).

В конце печатается таблица статистики:

- `Requests` — число запросов;
- `Granted` — число успешных выдач;
- `Waited` — число случаев ожидания;
- `Avg wait (ms)` — среднее время ожидания.

## Ограничения

- Реализован один тип ресурса (скаляр, не вектор ресурсов).
- Симуляция вероятностная: порядок событий и метрики зависят от случайных значений и планировщика потоков.
- Отсутствие deadlock обеспечивается только при использовании доступа к ресурсу через API `ResourceMonitor`.
